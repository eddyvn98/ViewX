# Hoàn Thiện Modern View Chart cho 100 User (2 Phase, Quick Tunnel giữ nguyên)

## Tóm tắt
Mục tiêu là đưa hệ thống hiện tại lên mức vận hành ổn định cho `~100 concurrent users` chủ yếu xem dữ liệu realtime, trong khi bot chỉ chạy khi web mở.

Ưu tiên thực hiện theo 2 pha:

1. Pha 1: hardening nhanh, sửa lỗi blocking, tối ưu WS/broadcast, đo tải thực tế.
2. Pha 2: chuẩn production hơn với `per-user auth`, giám sát, và chuẩn hóa triển khai.

## Kết luận rà soát hiện tại (điểm bắt buộc xử lý trước)
1. `MAX_WS_CLIENTS=80` trong `.env` đang thấp hơn mục tiêu 100 user.
2. `user.routes.js` có lỗi route nghiêm trọng: `router.route("/").getcheckLogin, User.getListUsers;` (route không được bind đúng).
3. Lint fail rất nặng (`854 vấn đề`, gồm nhiều lỗi hooks/types), cần khoanh vùng “production lint baseline” để tránh regression.
4. `ACCESS_TOKEN` đang đi qua query string (HTTP + WS + mobile link), rủi ro lộ token cao qua log/history.
5. WS broadcast hiện chạy vòng lặp mỗi giây và gửi per-client; chưa có backpressure/heartbeat rõ ràng.
6. Đang dùng Cloudflare Quick Tunnel, có rủi ro đổi URL/429/đứt kết nối.

## Scope đã chốt
1. Load profile: đa số view-only.
2. Public access: giữ Quick Tunnel ở giai đoạn này.
3. Auth model đích: per-user auth.
4. Delivery: 2-phase.

## Thiết kế triển khai chi tiết

## Phase 1 (Hardening nhanh để chạy 100 users)

### 1) Sửa lỗi blocking và khóa cấu hình runtime
1. Sửa route bug ở `backend/modules/user/user.routes.js`.
2. Tăng `MAX_WS_CLIENTS` lên `150` (headroom cho bridge + reconnect burst).
3. Thêm kiểm tra env cứng ở startup cho các key bắt buộc: `PORT`, `URL_MONGOOSE`, `ACCESS_TOKEN`, `MAX_WS_CLIENTS`, `WS_MSG_RATE_PER_10S`.
4. Chuẩn hóa `run-all.ps1` để luôn dùng build production nếu có `.next/BUILD_ID`, và fail-fast nếu thiếu.

### 2) Ổn định WebSocket path cho 100 concurrent
1. Thêm heartbeat (`ping/pong`) và timeout close cho client stale.
2. Thêm send guard/backpressure:
   - Nếu `ws.bufferedAmount` vượt ngưỡng thì skip frame non-critical (`priceUpdate`) cho client đó.
   - Không để 1 client chậm kéo tụt loop chung.
3. Tối ưu broadcast:
   - Cache payload theo `symbol/topic` trong tick hiện tại, tránh `JSON.stringify` lặp lại nhiều lần.
   - Giảm quét full map clients bằng index subscription (topic/symbol -> set ws).
4. Gắn metric runtime:
   - `ws_connected`, `ws_dropped_rate_limit`, `ws_dropped_backpressure`, `broadcast_loop_ms_p95`.

### 3) Hardening API/Tunnel tối thiểu (vẫn giữ Quick Tunnel)
1. Giữ `access_token` tạm thời cho tương thích, nhưng:
   - Ưu tiên `Authorization: Bearer`.
   - Mask token trong log.
   - Không ghi token vào file public (`public/mobile-access.json`) ở plain text.
2. CORS whitelist rõ và chặt hơn theo domain runtime thực tế.
3. Thêm rate-limit riêng cho endpoint nặng (`/api/ai/bridge/task`, market endpoints).

### 4) Baseline chất lượng code
1. Tách ESLint scope:
   - `lint:critical` cho thư mục runtime server (`backend/**`, hooks websocket chính, scripts server).
   - `lint:full` giữ nguyên để cleanup dần.
2. Rule: merge vào nhánh chạy server phải pass `lint:critical + build`.

### 5) Kiểm thử tải và tiêu chí đạt (Phase 1 gate)
1. Test 100 WS clients giả lập trong 15 phút.
2. Mục tiêu:
   - Tỷ lệ disconnect bất thường < 1%.
   - `p95 broadcast loop < 250ms`.
   - CPU trung bình < 70%, RAM free không tụt liên tục.
3. Chaos nhẹ:
   - Restart bridge, tunnel rotate URL, DB reconnect; dịch vụ phục hồi tự động qua watchdog.

## Phase 2 (Productionize theo per-user auth)

### 1) Chuyển auth từ shared token sang per-user
1. API auth endpoints:
   - `POST /api/auth/login`
   - `POST /api/auth/refresh`
   - `POST /api/auth/logout`
2. WS handshake:
   - Dùng JWT ngắn hạn trong header hoặc subprotocol, bỏ query token.
3. Role/permission:
   - `viewer` (xem dữ liệu)
   - `trader` (thao tác lệnh)
   - `admin` (quản trị)
4. Thêm `session revocation` và TTL rõ ràng.

### 2) Quan sát và vận hành
1. Structured logging (JSON) cho backend + bridge.
2. Metrics endpoint riêng:
   - `/api/metrics` (chỉ nội bộ/token admin).
3. Cảnh báo cơ bản:
   - Bridge offline > N phút.
   - WS drop spike.
   - DB disconnected.

### 3) Nâng chuẩn tunnel/public access (khi sẵn sàng)
1. Giữ Quick Tunnel ở ngắn hạn.
2. Chuẩn bị đường nâng cấp sang Named Tunnel + domain cố định để giảm downtime do URL đổi.
3. Tài liệu hóa runbook incident theo 3 tình huống: tunnel 429, bridge crash, DB down.

## Thay đổi API/interface/types quan trọng
1. `requireAccessToken` -> `requireAuth` (hỗ trợ JWT user + fallback token tạm thời ở Phase 1).
2. WebSocket connection contract:
   - Hiện tại: `?access_token=...`
   - Đích: `Authorization` hoặc `Sec-WebSocket-Protocol` token.
3. `health` response thêm trường metrics runtime:
   - `ws_buffer_pressure`
   - `broadcast_p95_ms`
   - `bridge_rtt_ms`.

## Test cases và scenario bắt buộc
1. Functional:
   - User viewer nhận được price/candle đúng symbol đã subscribe.
   - Bridge reconnect không làm treo WS clients.
2. Security:
   - Token sai/hết hạn bị từ chối cho cả HTTP và WS.
   - Không lộ token trong logs/artifacts public.
3. Performance:
   - 100 concurrent users, 15 phút soak.
   - Spike 0 -> 100 users trong 60 giây.
4. Reliability:
   - Restart từng thành phần (FE/BE/Bridge/Tunnel) và xác nhận tự phục hồi.
5. Regression:
   - `npm run build` pass.
   - `lint:critical` pass.

## Assumptions và default đã chốt
1. Tải chính là xem dữ liệu; không yêu cầu chạy bot server-side 24/7 ở giai đoạn này.
2. Tiếp tục dùng Quick Tunnel trong ngắn hạn dù có rủi ro URL/rate-limit.
3. Triển khai theo 2 phase, ưu tiên ổn định nhanh trước.
4. Máy hiện tại (i5-1135G7, RAM 16GB) đủ cho mục tiêu 100 view users nếu tối ưu WS và có backpressure.
